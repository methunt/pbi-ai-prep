# PRD Quality Review — PBI AI Prep

## Overall verdict

This is a genuinely strong PRD on the axes that matter most for its shape: it has a thesis ("spends its own effort on the part nobody has built — the write path", §1), the FR consequences are unusually concrete for a solo-build doc, and the counter-metrics (SM-C1..C3) are real counter-metrics rather than decoration. What is at risk is done-ness precision in a handful of FRs where an adjective is doing a bound's job (FR-8 "remains responsive", FR-9 "without perceptible scroll lag"), a small set of FRs that quietly carry mechanism the addendum already owns (FR-13, FR-22, FR-25, FR-27), and — most seriously — a §9.1 In Scope list that claims all 29 FRs for an MVP the brief's own decision log says must ship in 2–4 days. §9.1 as written is not a scope statement; it is the table of contents of §4 with FR ranges appended, and it does the opposite of scope work.

## Decision-readiness — strong

Decisions are stated as decisions, and the ones that hurt are named rather than smoothed. §2.2 Non-Users is the clearest example: "Firefox and Safari users. The directory picker does not exist in those engines" is a decision with the cost stated, and §8 restates it as "Not cross-browser. Firefox and Safari are excluded by capability, not by choice" — the distinction between capability and preference is exactly the honesty this dimension asks for. Similarly §8 "Not a readiness scorer... Semanticus Studio does that; this tool edits" concedes a competitor's territory outright.

Trade-offs generally name what was given up. FR-12's fourth consequence gives up DAX correctness on rename and says so: "the tool does not rewrite those expressions" with the assumption tagged. §9.2 gives up in-tool diff and names the substitute (`git diff`) rather than pretending the gap does not exist. §5 "Round-trip fidelity is the correctness bar. No feature ships if it can corrupt a model" is a stated priority order, not a balance.

The Open Questions in §11 are genuinely open and each carries a resolution method or a consequence — Q1 names the experiment ("Resolve by renaming in Desktop and diffing the TMDL"), Q5 and Q6 are live picks. None of them answer themselves in the next sentence. The one gap in decision-readiness is Q7: `qnaEnabled: true` is asked about but no FR references it, so if the answer is "yes, required", there is no requirement to attach the resolution to — and per the decision log the reference model already has `qnaEnabled: true`, meaning every model the author has tested against masks the failure case.

The `[NOTE FOR PM]` at §4.1 FR-4 ("stores handles, not paths, and cannot display a full filesystem path") is at a real tension — it constrains what the recent-projects UI can say. Two-note density across a 515-line PRD is low but defensible at these stakes; the missing note is on the schedule tension (see Scope honesty).

### Findings
- **medium** Open Question 7 has no FR to land on (§11 Q7, §4.4) — "Does `definition.pbism` need `qnaEnabled: true` before Prep for AI content has any effect, and should the tool offer to set it?" No FR in §4.4 covers detecting or setting `qnaEnabled`, and FR-3 only validates the `.pbism` *version*. If the answer is yes, a user's entire Prep for AI session silently does nothing. *Fix:* add a consequence to FR-3 or FR-15 covering `qnaEnabled` detection and a stated behaviour (warn / offer to set), so Q7's resolution has a home.
- **low** No trade-off stated for the deferred-parse UX (§4.2 FR-8) — deferral is chosen, but the cost to the user (first Prep for AI open pays the whole LSDL parse) appears only in the addendum's "with a visible loading state". *Fix:* add that visible-loading-state expectation as an FR-8 consequence so the trade-off is visible in the PRD.

## Substance over theater — strong

No persona theater. §2 has no personas at all — it has Jobs To Be Done, Non-Users, and four UJs with named protagonists who each carry a distinct constraint: Ravi is scale (2,000 objects, 180 empty descriptions), Sofia is the LSDL layer, Dan is context-before-writing, Priya is the no-install constraint. Each maps to a feature group that would be hard to justify without it — UJ-3 is the sole justification for §4.5, and the PRD says so ("Realizes UJ-3" on FR-19, FR-20, FR-21).

The Vision (§1) could not swap into another PRD: "The Prep data for AI dialog handles one field at a time and needs Power BI Desktop running. Tabular Editor does bulk metadata but needs a Windows install and never touches the linguistic schema." That is a specific competitive claim, and the decision log confirms it was earned by a competitor scan, not assumed.

NFRs in §5 are mostly product-specific rather than boilerplate — "Zero server... Every byte of model data stays in the browser tab", "Failure legibility. Every refusal and every failure names the file, the value found, and what was expected". The last is a real, checkable NFR and FR-3's "Every refusal names the file inspected and the value found" is its instantiation. Two NFRs slip toward adjective: the Performance bullet's "remain responsive" and the Accessibility bullet's "Focus order is predictable" (see Done-ness).

The success metrics are not activity metrics. SM-3 ("100 descriptions written in under 10 minutes using keyboard navigation only") measures the thesis — bulk keyboard editing — and SM-C1/SM-C2 explicitly counterbalance it. SM-C3 "Feature count... Every feature added past the write path dilutes the one thing this tool does that nothing else does" is the most substantive line in §10 and is doing genuine strategic work.

### Findings
- **low** SM-5 is the only weak metric (§10) — "the repository is used by someone other than the author, evidenced by an issue, a pull request, or a direct report of use" with `[ASSUMPTION: no numeric target set]`. For a stated portfolio project this is honest rather than theatrical, but it validates no FR and the PRD does not say which FR it would falsify. *Fix:* either attach it to the open-source NFR in §5 explicitly, or state plainly that SM-5 is a project-level signal, not a product metric.

## Strategic coherence — strong

The thesis is stated and load-bearing: "It borrows its read path from two MIT-licensed projects that already solved it, and spends its own effort on the part nobody has built — the write path" (§1). Everything downstream honours it. §4.6 is described as "The part that must not go wrong". §5's first NFR makes fidelity the correctness bar. SM-1 and SM-2 are both write-path metrics and are the two primary metrics. SM-C3 protects the thesis against feature creep. The MVP scope kind is coherently *problem-solving*, not platform or experience.

Prioritisation follows the thesis rather than ease: the read path is explicitly the borrowed, cheap part, and the doc spends its FR budget on write (FR-22..FR-25, four FRs and the only FR whose consequence demands "An automated check verifies this against the reference model in the repository", FR-23).

The one coherence strain is §4.7. Optional AI Assistance is four FRs (FR-26..FR-29) for a capability the thesis calls a dilution risk (SM-C3) and the counter-metric SM-C1 actively discourages succeeding at. The decision log records this as a user override — "AI features (BYOK drafting) stay in v1, not cut" — so it is a deliberate call, but the PRD never acknowledges the tension between §4.7 and SM-C1/SM-C3. A reader without the decision log sees a PRD arguing against its own §4.7.

### Findings
- **medium** §4.7 sits in tension with SM-C1 and SM-C3 and the PRD does not say so (§4.7, §10) — SM-C3 states "Every feature added past the write path dilutes the one thing this tool does that nothing else does", yet §4.7 adds four FRs past the write path. *Fix:* add a `[NOTE FOR PM]` at §4.7 naming the tension and the reason AI assistance is in v1 anyway (it is the portfolio-visible differentiator), so the counter-metrics read as deliberate rather than contradictory.

## Done-ness clarity — adequate

Most FRs clear the bar comfortably, and a few are exemplary. FR-11's "Tab and Shift+Tab move between editable cells; Enter commits and moves down; Escape reverts the cell" is a complete keyboard contract an engineer can build and a tester can drive. FR-3's version thresholds are exact ("a version below 4.0 is refused", "`definition/version.json` is absent or below 2.0.0"). FR-23's "Every file in the definition tree is byte-identical before and after an edit-free save" is the single most testable line in the document. FR-5's eight consequences each name a TMDL construct and its expected classification — `type: calculated`, `calculationGroup`, `extendedProperty ParameterMetadata` — so "done" for the parser is enumerable.

But the PRD is not uniformly rigorous, and the failures cluster in exactly the places where an engineer will need a number. Four consequences are adjectives standing in for bounds:

1. FR-8: "The interface remains responsive to input throughout parsing." Responsive is unmeasurable. Every implementation passes this on the author's laptop and fails on a colder machine.
2. FR-9: "Rows render at 2,000 objects without perceptible scroll lag." *Perceptible* is a person, not a threshold.
3. §5 Performance: "Grid scroll and filter remain responsive at that size" — the same adjective at NFR level, so there is no numeric fallback to inherit.
4. §5 Accessibility: "Focus order is predictable and visible focus indicators are present." Predictable to whom? There is no reference to a standard (WCAG 2.1 AA, or a stated tab-order rule).

A second class of problem: consequences whose verification condition is genuinely absent, not merely soft.

- FR-10: "The count of matching rows and the count of edited rows are both visible." Visible where, and edited-since-what — since load, or since last save? FR-14's pending-changes list implies since last save, but nothing says it.
- FR-11: "Multi-line descriptions are supported" — with a 500-character cap and a 200-character marker, but nothing states whether the 500 cap counts newlines, and the addendum's "each line gets its own `///` prefix" means the on-disk cost differs from the counted length. An engineer must guess.
- FR-16: "Existing synonyms are listed per object with their state, so generated and suggested terms are distinguishable from authored ones." The state values are never enumerated in the PRD — the decision log has `User/Generated/Suggested/Deleted` and the addendum has `Authored`, but the PRD says only "authored", "generated", "suggested", "tombstoned". FR-16 and FR-17 both use "authored state" as though it were a defined term; §3 does not define it.
- FR-19: "A table node can be expanded to show its columns." No default state stated (expanded or collapsed at load), which at 32 tables is a visible product decision.
- FR-21: "A grid row offers a path to that object on the canvas." *Offers a path* is the vaguest consequence in the document — the reciprocal consequence one line above it is specific ("opens the grid filtered or scrolled to that object") while this one names no mechanism, no target state, and no observable result.
- FR-24: "A revoked or expired permission prompts for re-grant rather than failing silently." Mid-save re-grant is a hard case — the addendum notes `requestPermission` throws outside a user gesture, so a mid-save prompt is not straightforwardly possible. The FR asserts a behaviour the addendum's own constraint makes doubtful, and neither says what happens to the half-written save set.
- FR-27: "The operation can be cancelled mid-run, keeping the suggestions already returned." No statement about the in-flight request or partial batches — and with the addendum's per-table batching, "already returned" is a batch boundary, not an object boundary. Done-ness here depends on a mechanism decision the PRD does not surface.

Also missing at the document level: nothing states what happens to *pending edits* on a rename that FR-12 warns about but does not block, and nothing gives a bound on the number of pending changes FR-14's list must handle — at 2,000 objects, the pending list is itself a virtualisation problem the PRD never sizes.

### Findings
- **critical** Four bounds are adjectives (§4.2 FR-8, §4.3 FR-9, §5 Performance, §5 Accessibility) — "remains responsive to input", "without perceptible scroll lag", "remain responsive at that size", "Focus order is predictable". Three of the four are the *only* statement of their bound, so there is nothing numeric to fall back to. *Fix:* replace with measurable thresholds — input latency budget in ms during parse (e.g. no main-thread block over 50 ms), scroll frame budget (60 fps / no frame over 16 ms at 2,000 rows), filter-apply latency at 2,000 rows, and name WCAG 2.1 AA for focus.
- **high** FR-21's reciprocal consequence is untestable (§4.5 FR-21) — "A grid row offers a path to that object on the canvas" names no mechanism and no resulting state, while its sibling consequence one line up is precise. *Fix:* state the observable: a grid row action switches to the Relationships tab with that object selected and centred, and the canvas selection state matches.
- **high** "Authored state" is used as a defined term but never defined (§4.4 FR-16, FR-17, and §3) — FR-16 "A synonym the user adds is written as authored", FR-17 "writes the entity's `Visibility` object with an authored state". The LSDL `State` enum (`User`/`Generated`/`Suggested`/`Deleted`, and `Authored` per the addendum) is nowhere in §3, so an engineer cannot tell whether "authored" is a UI concept or a literal serialised value. *Fix:* add an **LSDL state** glossary entry enumerating the values and which the tool writes, and make FR-16/FR-17 reference the enum rather than the adjective.
- **medium** Description length semantics are ambiguous (§4.3 FR-11) — "accepts up to 500 characters", "The 200-character position is marked", "Multi-line descriptions are supported". Whether newlines count toward 500, and whether the 200-character marker measures the decoded text or the `///`-prefixed on-disk form, is unstated. The addendum settles the LSDL analogue ("The 10,000-character limit counts the decoded string") but not this one. *Fix:* state that both counts apply to the decoded description text including newline characters, excluding `///` prefixes.
- **medium** FR-24's re-grant consequence may be unbuildable as written (§4.6 FR-24 vs addendum "File layer" item 5) — "A revoked or expired permission prompts for re-grant rather than failing silently" against "`requestPermission` only from a user gesture, since it throws otherwise". A mid-save revocation has no user gesture available. *Fix:* restate as: the save aborts, the files already written are reported per FR-24, and the interface presents a user-initiated retry that re-requests permission.
- **medium** FR-14 has no size bound (§4.3 FR-14) — the pending-changes list must hold changes for a model the PRD sizes at 2,000 objects, and FR-27 can generate a suggestion for every row in the current filter, so the list can plausibly hold 2,000 entries. No performance or rendering expectation is stated. *Fix:* add a consequence bounding pending-list render at the same object scale as the grid.
- **low** FR-10's edited-row count has no baseline (§4.3 FR-10) — "the count of edited rows" does not say edited since load or since last save. *Fix:* state "since the last successful save", matching FR-14.
- **low** FR-19 does not state the default node expansion state (§4.5 FR-19). *Fix:* state collapsed-by-default with expand on demand.
